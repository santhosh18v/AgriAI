# Dataset Provenance — PlantVillage (color, 8 approved classes)

This document records exactly what was fetched, from where, under what
licence terms, and what has (and has not) been done to it. It is the
authoritative source for dataset provenance; `ml-service/README.md` only
points here.

## Source

- **Upstream repository**: `https://github.com/spMohanty/PlantVillage-Dataset`
- **Default branch** (resolved dynamically via `git ls-remote --symref`, not
  hardcoded): `master`
- **Upstream commit SHA fetched**: `7f7ecc7e1eaca78107e3affe7cb5abd9427e139a`
- **Fetch method**: `git clone --filter=blob:none --no-checkout --sparse`,
  followed by `git sparse-checkout init --no-cone` with an explicit pattern
  list (chosen over cone mode because the fetch set mixes individual
  root-level files with specific nested directories, which cone mode does
  not handle unambiguously).
- **Fetch date**: recorded per-run in `ml-service/data/reports/source_integrity.json`
  (`fetch_date_utc`), generated by `training/prepare_dataset.py`.

`leaf_grouping/` was deliberately **not** fetched: `leaf-map.json` (fetched)
is the already-aggregated output of `leaf_grouping/aggregate_map.py` run

that join, it never needs to regenerate it, so the raw source CSVs and
`Google Leaf Counts.zip` serve no functional purpose here.

## Important correction: no `splits/` directory upstream

An earlier draft of this pipeline incorrectly assumed `splits/color_train.txt`
and `splits/color_test.txt` existed in this repository (they were seen on a
*different*, unapproved source — the Hugging Face mirror
`huggingface.co/datasets/mohanty/PlantVillage` — during earlier research).
**This was verified to be wrong** via `git ls-tree -r HEAD -- splits`
against the actual upstream commit, which returns nothing — no `splits/`
directory exists in `spMohanty/PlantVillage-Dataset` at
`7f7ecc7e1eaca78107e3affe7cb5abd9427e139a`. Files briefly fetched from the
Hugging Face mirror were deleted and are **not** part of this dataset copy.
No split files were obtained from Hugging Face, Kaggle, Zenodo, or any other
secondary source. **Milestone M3B builds our own deterministic 70/15/15
grouped split** directly from the fetched color images and `leaf-map.json`
instead of relying on any upstream-provided split.

## Licence and usage restrictions (approved, M2)

Treated as **CC BY-SA 3.0**, per the AIcrowd/crowdAI challenge's explicit,
directly-verified statement: *"All images are released under the Creative
Commons Attribution-ShareAlike 3.0 Unported (CC BY-SA 3.0), with the
clarification that algorithms trained on the data fall under the same
license."* Corroborated by the official `plantvillage.psu.edu` site
("Creative Commons 3.0 Share and Share Alike"). No `LICENSE` file exists in
the GitHub repository itself; the Hugging Face mirror's own dataset-loading
script (`plant_village.py`) marks its license field as *assumed, not
verified* by its author.

**Approved uses**: private training, academic evaluation, internal AgriAI
demonstrations only.

**Explicit prohibitions**:
- Dataset images must never be committed to this repository.
- Only source code, manifests, reports, and reproduction instructions may be
  committed — never image bytes.
- Trained weights are not published during Phase 2.
- The trained model must never be described as permissively licensed.

**Required gate**: any future public release of weights, or commercial
deployment, requires a separate licence/legal review — the AIcrowd source
explicitly states trained algorithms fall under the same licence as the
data.

## Major limitation — blocks Milestone M3B

- `leaf-map.json` contains **zero entries for either selected Corn class**
  (`Corn_(maize)___healthy`, `Corn_(maize)___Common_rust_`) — verified by
  direct inspection, not a join-logic bug.
- **Corn Healthy: 0% leaf-ID coverage** (0/1,162 matched).
- **Corn Common Rust: 0% leaf-ID coverage** (0/1,192 matched).
- **3,936 images are currently quarantined** (all of both Corn classes,
  plus unmatched Tomato Healthy/Late Blight/Early Blight images) — excluded
  from any split by default, per the no-singleton-fallback policy.
- **No train/validation/test split has been generated.** M3A is
  discovery/reporting only.
- **Milestone M3B is blocked** until a scientifically defensible grouping
  strategy is explicitly approved for images that have no `leaf_id` match —
  most urgently for the two Corn classes, which have no leaf-grouping
  coverage at all and cannot rely on the `leaf_id`-primary approach used
  for Tomato/Potato. Grouping these images purely by unreviewed pHash
  clustering, or by any other automatic fallback, is not authorized.

## Known gap discovered during M3A: `leaf-map.json` has zero Corn coverage

Verified directly: `leaf-map.json` contains **no entries at all** for either
Corn class (`Corn_(maize)___healthy`, `Corn_(maize)___Common_rust_`) — this
is a genuine gap in the upstream leaf-grouping metadata (consistent with
`leaf_grouping/filtered_leafmaps/` containing only 31 CSVs, not covering all
38 upstream classes), not a bug in the join logic. All Corn images are
therefore unmatched by `leaf_id` and, absent human-reviewed pHash grouping,
are quarantined by default (see `ml-service/data/reports/quarantine_report.json`
and `leaf_id_join_summary.json`). This is a material input for Milestone
M3B's grouping strategy, not something resolved in M3A.

## Milestone M3B-1: Tomato authoritative leaf-ID recovery investigation

M3B planning (see the approved M3B report) identified a plausible recovery
path: three `leaf_grouping/filtered_leafmaps/*.csv` files — the exact input
set `leaf_grouping/aggregate_map.py` consumes — were never fetched during
M3A. M3B-1 fetched only these three files (plus `aggregate_map.py` and
`create_map.py`, for inspection only, never executed) from the same
approved upstream repository at the same recorded commit, and tested
whether they contain leaf-count rows for the 1,582 currently-unmatched
Tomato images.

**Fetched, from `https://github.com/spMohanty/PlantVillage-Dataset` at
commit `7f7ecc7e1eaca78107e3affe7cb5abd9427e139a`**:

| File | Size | SHA-256 | Rows | Columns |
|---|---:|---|---:|---|
| `leaf_grouping/filtered_leafmaps/Tomato___healthy.csv` | 25,590 B | `e28d9b7f4713d8fa0140741ac8cd23d2d3016f34246a527fec8b90d97a7e410c` | 1,000 | `File Name`, `Leaf #` |
| `leaf_grouping/filtered_leafmaps/Tomato___Early_blight.csv` | 29,637 B | `5318a8db263bf2c9655b04c8b601954f53761a40cefb2cca928ad9dc50e305be` | 1,000 | `File Name`, `Leaf #` |
| `leaf_grouping/filtered_leafmaps/Tomato___Late_blight.csv` | 27,190 B | `23b855a3eaf5b427546cda0877a6f711c6680dcf03dacc4dc398ac0cce4819c2` | 920 | `File Name`, `Leaf #` |

All three: clean UTF-8, no BOM, zero duplicate `File Name` rows, zero blank
`File Name`/`Leaf #` values, zero malformed rows.

**Method**: `ml-service/training/recover_tomato_leaf_ids.py` ports
`aggregate_map.py`'s exact normalization (`".".join(name.split(".")[:-1])`
then `.lower().strip()`, verbatim from the upstream Python 2 script — not
an invented rule) to Python 3, builds the same `{normalized_filename:
[leaf_id, ...]}` map from just these 3 CSVs, and attempts a lookup for
every one of the 1,582 unmatched Tomato images (after stripping the same
UUID prefix the M3A join already handles).

**Direct evidence found, not inferred**: filename-prefix-family analysis of
all rows in all three CSVs shows each file covers **exactly one** naming
family — `Tomato___healthy.csv` is 1,000/1,000 rows `RS_HL *`;
`Tomato___Early_blight.csv` is 1,000/1,000 rows `RS_Erly.B *`;
`Tomato___Late_blight.csv` is 920/920 rows `RS_Late.B *`. These row counts
match almost exactly the *already-matched* counts from M3A (999, 999, 920)
— confirming these CSVs are precisely the source of the existing
`leaf-map.json` Tomato entries. **None of the three CSVs contain any row
for the `GH_HL Leaf *` (Tomato Healthy) or `GHLB*/GHLB_PS Leaf *` (Tomato
Late Blight) filename families that make up the unmatched images.**

**Recovery result: 0 of 1,582 unmatched Tomato images recovered.**

| Class | Unmatched before | Exact match | Normalized match | Ambiguous | Malformed | No match | Recovered % |
|---|---:|---:|---:|---:|---:|---:|---:|
| Tomato Healthy | 592 | 0 | 0 | 0 | 0 | 592 | 0.0% |
| Tomato Early Blight | 1 | 0 | 0 | 0 | 0 | 1 | 0.0% |
| Tomato Late Blight | 989 | 0 | 0 | 0 | 0 | 989 | 0.0% |

**Conclusion**: this is not a normalization bug and not a join-logic gap —
it is now directly confirmed (by reading the actual CSV rows, not by
absence-of-file inference as with Corn) that the original PlantVillage
leaf-counting effort never logged the `GH_HL`/`GHLB*` filename family at
all for these three classes. Authoritative recovery (Strategy A from the
M3B plan) is exhausted for Tomato via this path. Remaining options for
M3B-2 are Strategy B (conservative, human-reviewed filename-family
grouping — the `GH_HL Leaf <N>` and `GHLB* Leaf <N>` conventions remain
structurally plausible source-family signals, just not authoritatively
confirmed) and Strategy C (reviewed pHash), per the approved M3B
comparison. No filename-family or pHash grouping was assigned in M3B-1 —
that decision remains explicitly deferred to M3B-2 human review.
